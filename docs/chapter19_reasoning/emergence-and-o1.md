# 16.1 从语言模型到推理模型

先看一个普通语言模型容易失败的场景。面对一道竞赛数学题，它可能读完题目就生成最熟悉的公式；如果第一步选错，后面的 token 只是在继续完成这条错误路径。代码任务也一样：模型可以一次写出补丁，却未必会先定位问题、运行测试，再根据失败结果修改方案。

推理模型改变的是这段执行过程。模型在给出最终答案以前，可以展开中间步骤、比较候选方法、调用工具并检查结果。额外计算只有在这些行为提高成功率时才有价值，因此训练目标、推理预算和结果验证必须一起改变。

第 16 章沿着这条变化展开：16.1 先说明推理模型为什么出现；16.2 进入 R1-Zero 的纯 RL 训练；16.3 讨论参数不变时怎样增加推理计算；16.4 和 16.5 解决预算控制；16.6 再处理推理内容怎样展示和监督。本节先回答四个问题：产品形态发生了什么变化，公开实验观察到哪些推理行为，RL 在其中强化了什么，以及系统怎样区分推理与最终答案。

## 1. o1 如何把推理能力带进产品

仍以数学题为例。直接回答模型只执行一次连续生成；推理模型允许在答案以前增加“列条件—尝试方法—检查—修正”的过程。o1 的意义在于把这套过程放进可调用的产品，并让用户可以用更多等待时间换取更高的任务成功率。

### 1.1 o1 怎样训练更长的推理过程

OpenAI 在 [o1 发布说明](https://openai.com/index/learning-to-reason-with-llms/)中公开的重点是训练与推理计算：模型用大规模 RL 学习怎样组织较长的内部推理，训练计算和单题思考时间增加时，评测表现都随之提高。官方没有公开完整奖励构成，因此不能把 o1 简化为“只用最终答案奖励”；能够确定的是，RL 直接优化了思考链在复杂任务中的有效性。

o1 发布时在几项推理基准上明显超过 GPT-4o：

- **AIME 2024**：GPT-4o 单次回答约为 12%，o1 单次回答约为 74%；对 64 条回答做多数选择时，o1 达到约 83%；
- **Codeforces**：o1 的 Elo 为 1673，位于参评人类选手的第 89 百分位；
- **GPQA Diamond**：o1 的单次回答约为 77%，GPT-4o 约为 51%。

单次回答、多数选择和重排序使用的推理计算不同。把指标写在一起时必须保留评测方式，否则读者会把“模型更强”和“采样更多”混为一谈。

o1 不向用户展示内部 CoT，只返回最终答案或经过整理的说明。这样可以减少内部推理被直接复制的风险，也使用户无法逐步检查模型实际经历的推理过程。因此，系统还需要用可验证答案、引用和外部评测建立可信度。

### 1.2 推理预算成为产品接口

模型能够从更多思考中获益以后，服务端还需要决定每次请求投入多少计算。OpenAI 在 2024 年 12 月发布正式版 o1 时加入 `reasoning_effort`，开发者可以选择较低或较高的推理投入。这个参数没有承诺固定 token 数，它表达的是质量、延迟和费用之间的档位。

OpenAI 同月预告 o3，随后在 2025 年 4 月正式发布。官方报告 o3 继续扩大了 RL 训练计算与推理计算，并在相同延迟和成本条件下超过 o1。这里重要的变化不在某一个不断更新的榜单数字，而在产品接口已经允许系统按任务调节推理投入。

第 16.3—16.5 节会依次把这个接口拆开：额外计算可以怎样使用，固定预算怎样设置，模型又怎样根据任务动态选择预算。

### 1.3 o3 与 o4-mini 把推理接入工具调用

2025 年 4 月发布的是 [o3 和 o4-mini](https://openai.com/index/introducing-o3-and-o4-mini/)，并不存在同次发布的“完整 o4”。这两个模型把网页搜索、Python、文件和图像分析等工具放进同一条解题过程：

- 模型在推理过程中可以主动调用工具（搜索、代码执行、图像分析）
- 工具调用的结果反过来影响下一步推理
- 形成"思考 → 调工具 → 再思考 → 再调工具"的循环

这种工作方式通常称为 **agentic reasoning**：模型在多轮推理中读取外部环境的反馈，再决定下一步动作。它与 [第 19 章 Agentic RL](../chapter22_agentic/overview) 讨论的工具调用和环境交互直接相关。

## 2. 竞赛编程如何验证推理训练

基准分数只能说明结果提高了，还不能解释模型在解题过程中做了什么。竞赛编程提供了更容易观察的环境：代码能否编译、测试是否通过、修改以后结果是否改善，都可以由工具记录。

o1 发布后，一个直接问题是：这些行为来自大量人工编写的推理链，还是可以通过结果反馈强化出来？

2025 年 2 月，OpenAI 发表 [Competitive Programming with Large Reasoning Models](https://arxiv.org/abs/2502.06807)（arXiv:2502.06807）。论文没有公开完整训练细节，因此下面只讨论可以从实验直接观察到的行为和计算分配。

### 2.1 端到端 RL 与专用流水线的比较

传统上，Codeforces 这类竞赛任务通常使用专门设计的流水线：

```text
问题 → 编译器 + 测试用例生成 → 程序合成 → 选择最优解
```

这个流水线里的每一步都由专门模块负责，例如搜索算法、程序生成和测试筛选。论文中的推理模型把这些行为放进同一条生成轨迹，并在报告的 Codeforces 设置上取得了更好的结果。这个对比说明，端到端训练可以学会组织候选生成、执行测试和修改方案，但结论仍受模型、任务和计算预算限制。

### 2.2 多阶段推理行为怎样出现

论文还记录了 o1 / o3 解决 Codeforces 题目时出现的多阶段推理行为，包括：

- **生成多个候选解**：模型自己生成多个解法，比较优劣
- **执行验证**：用工具执行代码，看结果是否符合预期
- **自我修正**：发现错误后重新推导
- **策略切换**：从贪心算法切换到动态规划，再切换到回溯

训练过程没有把“先尝试贪心，再尝试动态规划”写成固定流程，但高质量预训练数据可能已经让基座模型见过这些方法。RL 的作用是提高能够通过测试的轨迹概率，使候选比较、执行验证和错误修正更稳定地出现。清晰的结果奖励提供了选择信号，基座模型已有的知识与采样覆盖范围则决定了有哪些行为可供强化。

### 2.3 训练算力与推理算力怎样分工

论文还报告了一个关键 trade-off：

- **增加训练算力**：模型的基础能力提升，但每道题的推理 token 数基本不变
- **增加推理算力**（让模型思考更久）：在固定训练算力下，可以进一步提升表现

训练算力决定模型已经掌握哪些方法，推理算力决定模型在当前题目上能够尝试和检查多少次。16.3 节会进一步比较这两类算力。

## 3. RL 创造能力还是激活能力

观察到模型会检查和修正以后，还要回答能力来源。若把所有变化都归结为 RL“创造了推理”，就会忽略基座模型已经从预训练数据中学到的数学、代码和语言模式。o1 和 R1-Zero 报告的“涌现”需要分成两层理解：

**含义一：推理行为从未在训练数据中显式出现**

R1-Zero 没有见过任何人工标注的 CoT，但训练后会自主生成长思维链、做反思、做验证。这种"涌现"是相对于训练数据而言的——模型没有被教过这样做。

**含义二：推理能力是否全部由 RL 阶段创造**

后续复现实验（如 SimpleRL-Zoo、Open-R1）表明，基座模型在 RL 以前已经能以一定概率生成正确推理。RL 根据奖励重新分配这些轨迹的概率，使有效方法更常出现，也可能在已有行为的组合上形成新的策略。因而，分析 RL 效果时要同时检查基座能力、采样覆盖和训练后的概率变化。

这个区分对实践很重要：

- 先在基座模型上进行多次采样，估计正确轨迹是否已经存在。
- 再比较 RL 前后的成功率和行为分布，判断问题主要是缺少能力，还是有效轨迹出现得太少。
- 最后根据差距决定补预训练、SFT 数据，还是增加 RL 数据与算力。

DeepSeek-R1 的实验也支持这种区分：预训练提供知识和基本推理能力，RL 让能够获得奖励的推理行为更稳定地出现。

## 4. 推理模型如何组织输出与工具

训练能够强化检查和修正以后，系统还要把这些行为组织成稳定接口。至少要区分三类内容：模型内部用于继续计算的推理状态、可以交给工具执行的动作，以及最终返回给用户的答案。混在一个文本流里，验证器就难以抽取答案，工具也难以判断何时执行。

公开模型采用了不同接口，可以按三个独立问题比较：

| 接口问题       | 代表做法                                                        | 需要继续解决的问题                 |
| -------------- | --------------------------------------------------------------- | ---------------------------------- |
| 是否进入长思考 | DeepSeek V3.1、Qwen3 在同一模型中支持思考与非思考模式           | 怎样判断当前任务需要哪一种模式     |
| 投入多少计算   | OpenAI `reasoning_effort`、Qwen3 thinking budget、Claude effort | 怎样让预算与任务难度匹配           |
| 向用户展示什么 | OpenAI 提供推理摘要，DeepSeek-R1 等模型可输出推理文本           | 展示内容能否检查、是否泄露敏感信息 |

模型名称和接口会更新，这三个问题却保持稳定。它们分别对应 16.4 的模式与预算、16.5 的自适应分配，以及 16.6 的推理链展示。

展示方式会影响用户检查、数据蒸馏和安全监控，16.6 节会单独展开。这里先看训练格式怎样把推理段与答案段分开。

### 4.1 推理 Token 与答案 Token 怎样分开

传统 LLM 输出只有一个 token 序列：`<答案 token>`。推理模型输出多了一个"推理 token"段：`<推理 token> <分隔符> <答案 token>`。

在工程实现上，这通常通过特殊 token 实现：

```text
<|begin_of_thought|>
用户的问题是要解决...让我先理解题意...
可以尝试的方法有...
第一种：... 这种方法的问题在于...
第二种：... 这种方法看起来可行...
让我验证一下...
是的，第二种方法得到正确结果。
<|end_of_thought|>
<|begin_of_solution|>
最终答案是 X。
<|end_of_solution|>
```

分隔以后，系统可以只抽取答案交给结果验证器，也可以对推理段施加长度约束或过程评价。分隔符本身不会自动提供正确性标签，但它为 Hybrid Thinking、思考预算和 long2short 建立了清楚的数据边界。

## 小结

o1 让“投入更多推理计算”成为可调用的产品能力，o3 与 o4-mini 又把工具反馈接入推理过程。竞赛编程实验进一步说明，端到端 RL 可以强化候选生成、执行验证和错误修正等行为；预训练模型已经具备的知识与采样覆盖范围，仍然限制 RL 能够强化什么。

[16.2 R1-Zero 纯强化学习推理](./r1-zero-pure-rl-reasoning) 将沿着奖励、组内比较和行为变化，具体说明不经过 SFT 冷启动时，这些推理行为怎样在训练中形成。
