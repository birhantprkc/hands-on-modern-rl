# 18.3 训练稳定性

上一节我们搭好了后训练闭环：**数据→SFT→RL→评测→数据回流**。真正开始跑训练以后，你打开监控面板，第一件事通常是看**奖励曲线**——哎，奖励从 0.4 涨到 0.7 了，看起来进步很大！但等你在**独立测试集**上一测，正确率根本没变，平均回答长度倒是涨了一倍。

这时候你遇到的不是算法问题，而是**训练稳定性问题**。模型可能只是学会了"写得更长更容易得高分"这种**奖励漏洞**；也可能某次更新后 loss 和梯度直接变成 **NaN**，后面的参数全废了；还有更隐蔽的问题：生成回答用的是**旧模型**，训练用的是**新模型**，两边版本对不上，记录下来的概率根本不是生成那条轨迹时的概率。

这些问题会反映在不同曲线上。只看奖励，无法区分模型真的学会了解题、利用了奖励漏洞，还是参数更新已经出错。因此，训练时需要把 **loss、梯度范数、KL、熵和独立评测**放到同一条时间线上比较。

## 从四类信号定位故障来源

把曲线放在同一条时间线上，先判断异常来自哪一层，再选择工具。四层之间有明确的因果顺序：数据和奖励决定模型学什么，策略指标描述模型怎样改变，数值指标反映参数能否正常更新，训练系统则决定日志中的概率是否真的来自生成回答的策略。

| 层次       | 主要信号                         | 首先检查什么                           |
| ---------- | -------------------------------- | -------------------------------------- |
| 数据与奖励 | 奖励升高，独立评测不变           | 奖励规则、数据重复、评测污染与回答长度 |
| 策略变化   | KL 快速升高或熵快速下降          | 更新幅度、KL 约束、采样难度与策略版本  |
| 数值更新   | loss、梯度范数暴涨或出现 NaN     | 学习率、计算精度、异常 batch 与裁剪    |
| 训练系统   | rollout 与训练端概率、版本对不上 | 权重同步、token、精度、算子与 MoE 路由 |

## 第一层：数据和奖励是否可信

先看训练奖励与独立评测是否一起提高。奖励上升、平均回答长度同时增加，而独立测试集正确率不变，说明模型学到的是更容易获得奖励的输出形式，目标能力并没有提高。模型也可能只记住训练任务，或者利用了答案解析器和测试程序的漏洞。

这一层先检查训练样本、答案解析器、测试环境和奖励方向，再检查训练集重复与评测污染。目标信号一旦出错，后面的优化越稳定，模型反而会越稳定地偏离真实目标。

## 第二层：策略是否移动过快

数据和奖励可信以后，再观察 KL 与熵。KL 衡量当前模型与参考模型的输出分布有多远；它快速升高，说明一次或连续多次更新把模型推离了原有能力范围。熵表示输出分布有多分散；它快速下降，说明少数 token 或回答模式占据了大部分概率，模型正在过早停止探索。

此时要比较采样时的旧策略与更新后的新策略，检查学习率、裁剪范围、KL 约束和经验是否已经过时。任务过于简单时，模型也可能很快集中到少数高奖励答案，因此数据难度要和策略指标一起看。

## 第三层：参数能否正常更新

loss 反映当前训练目标的变化，梯度范数反映这一步准备把参数推多远。两者突然暴涨，或者直接出现 NaN，说明单步前向、反向或参数更新发生了数值问题。排查时先固定一个 batch 重复运行，再检查学习率、低精度计算、梯度裁剪、异常样本和优化器状态。

AdamW、Muon 以及各种 clipping 方法都作用在这一层：它们把梯度转换成更可控的参数更新。优化器无法修复错误奖励、损坏的数据，也无法让生成端与训练端自动使用同一模型版本。因此，看到 loss spike 时可以检查优化器；看到奖励与评测分离时，继续更换优化器没有意义。

## 第四层：系统是否在训练同一个策略

前三层都正常时，最后核对 rollout 引擎与训练引擎。生成端可能使用稍早的模型版本、FP8 精度和一套推理算子，训练端则使用更新后的权重、BF16/FP32 和另一套算子。两边即使读取同一份参数，token 的 log probability 仍可能存在偏差；MoE 模型还会受到专家路由差异影响。

这一层要逐项对齐模型版本、token、log probability、计算精度和专家路由，确认训练日志描述的旧策略就是实际生成轨迹的策略。[18.4](./distributed-sync) 将继续展开权重同步和训推一致性。

四层排查必须按顺序进行：先确认模型学的目标正确，再看策略有没有移动过快，然后检查单步更新，最后核对分布式系统。这样才能避免用数值工具修奖励问题，或用数据清洗掩盖权重同步错误。

## 从四个公开案例看四层故障

下面保留 GLM、Llama、Seed 与 Kimi 的完整公开案例。它们不是四个连续训练步骤，而是分别说明四层中的不同问题：GLM 展示 MoE 和多阶段训练的系统约束；Llama 4 展示架构变化以后评测为什么也要改变；Seed-Thinking 展示数据难度怎样影响奖励信号；Kimi K2 则直接处理参数更新和注意力计算中的异常值。

| 案例              | 重点观察什么                   | 对应的失稳信号                   |
| ----------------- | ------------------------------ | -------------------------------- |
| GLM-4.5 / GLM-4.6 | MoE 路由、多阶段训练与模式切换 | 专家负载失衡、阶段间能力回退     |
| Llama 4           | 多模态、长上下文与评测版本     | 训练分数与真实任务表现不一致     |
| Seed-Thinking     | 数据难度、课程学习与自我验证   | 奖励过稀、组内优势接近于零       |
| Kimi K2           | 优化器更新与注意力分数         | loss spike、梯度或注意力数值异常 |

## GLM：多阶段训练怎样影响系统稳定性

[GLM-4.5](https://github.com/zai-org/GLM-4.5)（智谱 AI，2025 年 7 月发布）和 GLM-4.6（2025 年 10 月发布）都采用多阶段训练。这个案例适合观察 MoE、推理 RL、通用 RLHF 和双模式输出怎样接在同一条训练线上。

### 模型架构给后训练带来的约束

先看模型本身给后训练带来了哪些约束：

- **MoE 架构**：GLM-4.5 共有 355B 参数，每次前向激活 32B 参数。RL 更新还要关注专家负载与路由稳定性。
- **Thinking 与 Non-Thinking 双模式**：同一模型需要学习何时展开推理、何时直接回答。
- **开放资料**：公开权重、训练方法和部分数据，为复现实验提供了入口。
- **代码与 Agent 能力**：训练数据需要同时覆盖代码生成、工具调用和多步执行。

### GLM-4.5 的五阶段训练流程

```text
┌──────────────────────────────────────────────────────────┐
│ Phase 1: Base 预训练（MoE 架构）                          │
│   - 15T tokens 高质量数据                                 │
│   - MoE: 355B total / 32B active                         │
│   - RoPE scaling 支持长 context                          │
├──────────────────────────────────────────────────────────┤
│ Phase 2: 通用 SFT                                         │
│   - 多语言对话数据                                        │
│   - 工具调用格式训练                                      │
├──────────────────────────────────────────────────────────┤
│ Phase 3: 推理 RL                                          │
│   - 数学、代码、推理任务                                  │
│   - GRPO + 规则奖励                                      │
│   - Self-validation 集成                                  │
├──────────────────────────────────────────────────────────┤
│ Phase 4: 通用 RLHF                                        │
│   - 对话质量、安全性                                      │
│   - Helpfulness / Harmlessness 双目标                    │
├──────────────────────────────────────────────────────────┤
│ Phase 5: Thinking / Non-Thinking 统一                    │
│   - 混合数据 SFT                                          │
│   - 让模型学会模式切换                                    │
└──────────────────────────────────────────────────────────┘
```

这条流程先用 SFT 建立基本行为，再用推理 RL 提高可验证任务的正确率，随后用通用 RLHF 修正对话质量与安全性，最后统一两种回答模式。[DeepSeek-R1 的训练流程](../chapter18_grpo/deepseek-dapo)采用了相近的阶段划分。

### GLM-4.6 的训练改进方向

GLM-4.6 继续调整推理长度、工具使用和模式控制：

- **更长的 Thinking**：支持 100K+ token 的长推理轨迹。
- **更多 Agent 工具**：覆盖搜索、代码执行和文件操作。
- **多模态协同**：与 GLM-4.5V 视觉模型配合。
- **更细的 Thinking Budget**：用户可以控制推理预算。

### GLM-4.6 的基准测试结果

| Benchmark     | GLM-4.5 | GLM-4.6 |
| ------------- | ------- | ------- |
| AIME 2025     | 75.3    | 83.6    |
| MATH-500      | 92.1    | 95.4    |
| LiveCodeBench | 56.2    | 62.7    |
| GPQA Diamond  | 68.5    | 72.4    |

这些基准分别检查数学、代码和科学推理能力。阅读结果时还要结合具体评测设置，不能用单个平均分判断训练是否稳定。

### GLM 的工程启示

这个案例给出三点工程信息：

1. **MoE 与推理 RL 要联合调试。** 除了奖励和 KL，还要监控专家负载、路由和跨卡通信。
2. **双模式需要单独评测。** Thinking 模式的正确率、长度和成本不能替代 Non-Thinking 模式的响应质量。
3. **代码与工具任务需要真实执行。** 静态答案分数无法覆盖环境状态、工具返回和长轨迹失败。

## 7. Llama 4：架构变化以后怎样保持评测一致

[Llama 4](https://ai.meta.com/blog/llama-4-multimodal-intelligence/)（Meta，2025 年 4 月发布）把 MoE、原生多模态和长上下文放在同一系列中。它展示了模型架构变化怎样继续影响后训练数据和评测方法。

### 模型系列与参数规模

Llama 4 包含三个变体：

- **Llama 4 Scout**：109B total / 17B active（MoE），10M context
- **Llama 4 Maverick**：400B total / 17B active，1M context
- **Llama 4 Behemoth**（未发布）：2T total / 288B active，Meta 内部训练

### 架构与训练改进

**原生多模态。**

Llama 4 从预训练阶段共同处理文本和图像 token。后训练因此需要同时准备文本任务、多模态任务和跨模态一致性评测。

**Early Fusion。**

Early Fusion 让文本与图像信息在模型较早的层中交互。多模态奖励也要判断回答是否真正使用了图像证据。

**MoE 架构。**

Llama 4 全系采用 MoE。每个 token 只经过部分专家，总参数可以增加，而单次前向的激活参数保持在较低水平；训练系统则要额外处理专家路由和通信。

**长上下文。**

Llama 4 Scout 支持 10M token 上下文，并使用 iRoPE（interleaved RoPE）和稀疏注意力。长上下文评测要同时检查证据检索、答案正确率和推理成本。

### 多阶段训练方法

Meta 没有公开完整训练细节。下面的阶段划分根据公开论文和博客整理，推测内容需要与官方披露区分：

```text
┌─────────────────────────────────────────────────────────┐
│ Phase 1: 多模态预训练                                   │
│   - 文本 + 图像 + 视频联合训练                          │
│   - 22T tokens 级别（推测）                            │
│   - Early fusion 架构                                  │
├─────────────────────────────────────────────────────────┤
│ Phase 2: Mid-training（中等规模 SFT）                  │
│   - 通用指令跟随                                        │
│   - 工具调用格式                                        │
├─────────────────────────────────────────────────────────┤
│ Phase 3: 后训练 RL                                      │
│   - RLHF + RLVR 混合                                   │
│   - Helpfulness / Safety / Reasoning 多目标           │
└─────────────────────────────────────────────────────────┘
```

### 公开评测与争议

Llama 4 的公开分数与实际使用体验曾出现差异，问题主要集中在两个方面。

**基准分数与真实任务表现。**

Llama 4 Maverick 在多个 benchmark 上分数高，但用户实际使用时感觉不如 Claude 3.5 / GPT-5。Meta 后来承认 benchmark 评估与实际体验有差距。

**评测版本与开源版本。**

LM Arena 上跑的 Maverick 是一个**经过专门优化的版本**——使用了 chat template 调整和 prompt engineering。开源的 Maverick 与 arena 版本有差异。

这类版本差异说明，比较模型时必须记录权重版本、聊天模板、系统提示和采样参数。[现代模型事故](../chapter30_alignment_failures/modern-incidents)还讨论了数据污染等评测风险。

### Llama 4 的工程启示

从训练系统角度看，这个案例留下三项可复用经验：

1. **MoE 需要独立的路由监控。** 总损失正常时，仍可能出现局部专家负载失衡。
2. **Early Fusion 改变了训练样本。** 文本与图像必须在同一任务中形成可检查的对应关系。
3. **长上下文增加了评测维度。** 除了能否装下输入，还要检查模型能否找到证据并控制生成成本。

## 8. Seed-Thinking：数据难度怎样改变策略信号

[Seed1.5-Thinking](https://arxiv.org/abs/2504.13914)（字节 Seed，2025 年 4 月）把数据整理、策略优化、自我验证和课程学习组合成一条推理训练流程。下面依次说明每个组件负责什么。

### 训练方案的核心组成

Seed-Thinking 的重点在于组合多个已有组件，并让它们在同一训练过程中协作。

**数据整理。**

```text
数学数据：
  - 高质量数学题（AIME、Putnam 历年题）
  - 自动生成题（用强 LLM 生成新题）
  - 难度分级（按 base model 的通过率）

代码数据：
  - Codeforces 题目（带测试用例）
  - SWE-bench / SWE-smith（带 PR 数据）
  - 函数生成（HumanEval 扩展）
```

**GRPO 与 DAPO 改进。**

Seed-Thinking 用了 [DAPO](../chapter18_grpo/deepseek-dapo) 的四项工程改造 + 一些新改进：

- **动态 KL**：训练初期 KL 强，后期减弱
- **Adaptive clip**：根据训练进度调整 clip range
- **Group size 调度**：早期大 group，后期小 group

**Self-Verification。**

让模型在生成答案后做自我验证：

```python
def self_verification_reward(response, ground_truth):
    answer = extract_answer(response)

    # 让模型重新读题、验证答案
    verification_prompt = f"检查这个答案是否正确：{answer}"
    verification = model.generate(verification_prompt)

    if "正确" in verification and answer == ground_truth:
        return 1.0  # 答对 + 验证通过
    elif "错误" in verification and answer != ground_truth:
        return 0.5  # 答错但识别出错误
    else:
        return 0.0  # 答错且没识别
```

这项奖励同时检查最终答案与自我校验结果。模型答错但能识别错误时仍保留部分信号，训练目标因而覆盖“作答”和“检查”两个步骤。

**Curriculum Learning。**

训练数据按难度排序，先让当前模型在较容易的任务上获得有效奖励，再逐步增加难度。这样可以减少训练初期整组样本全部失败、优势信号接近于零的情况。

### 公开评测结果

Seed-Thinking 1.5 在多个 benchmark 上：

| Benchmark         | 分数  |
| ----------------- | ----- |
| AIME 2024         | 86.4% |
| MATH-500          | 96.2% |
| GPQA Diamond      | 75.1% |
| Codeforces Rating | 1822  |

这些结果反映了整套训练方案在数学、科学推理和代码任务上的表现。产品部署还需要继续检查回答长度、推理延迟和通用能力回归。

## 9. Kimi K2：怎样限制异常参数更新

[Kimi K2](https://arxiv.org/abs/2507.20534)（Moonshot，2025 年 7 月）同时使用 MuonClip 和 QK-clip 控制训练中的异常更新。前者作用于参数更新，后者作用于注意力分数。

### Muon 优化器

[Muon](https://kellerjordan.github.io/posts/muon/)（2025 年 2 月）结合动量与正交化：

- **Momentum**：累积连续更新中的方向信息。
- **Orthogonalization**：对更新矩阵进行正交化处理。

正交化重新调整更新矩阵的奇异值，限制某些方向过度放大。它处理的是优化器层面的更新形状。

### MuonClip 的更新约束

下面的简化代码展示裁剪发生的位置：

```python
def muon_clip_update(grad, momentum, clip_threshold=1.0):
    # Muon 主流程
    momentum = beta * momentum + (1 - beta) * grad
    orthogonalized = orthogonalize(momentum)

    # Clip 防止爆炸
    norm = torch.norm(orthogonalized)
    if norm > clip_threshold:
        orthogonalized = orthogonalized * (clip_threshold / norm)

    return -lr * orthogonalized
```

裁剪限制单步更新范数，减少异常 batch 对参数造成的突变。它仍需与学习率、梯度监控和数据检查一起使用。

### QK-clip 与注意力稳定性

QK-clip 直接限制注意力中 $QK^\top$ 的取值范围：

```python
def attention_with_qk_clip(Q, K, V, clip_value=30.0):
    # 标准 attention
    scores = Q @ K.T / sqrt(d)

    # QK-clip: 防止 attention scores 过大
    scores = torch.clamp(scores, min=-clip_value, max=clip_value)

    # Softmax + 加权
    attn = softmax(scores)
    output = attn @ V

    return output
```

长上下文中的注意力分数可能持续增大，使 Softmax 过度集中到少数 token，并放大数值误差。QK-clip 在进入 Softmax 前限制分数范围，从注意力计算这一层减少异常值。

### 训练效果

公开结果从稳定性、速度和最终能力三个方面报告这套组合：

- **训练稳定性**：loss spike 从平均每 1T tokens 一次降低到每 10T tokens 一次。
- **训练速度**：相较 Adam 提高约 15%。
- **最终性能**：Kimi K2 在多项公开基准上取得较高结果。

### MuonClip 的工程启示

这个案例说明，稳定性工具需要对应到具体故障层级：

- **参数更新层**：MuonClip 限制异常更新的范数。
- **注意力计算层**：QK-clip 限制长上下文中的极端注意力分数。
- **工程实现层**：训练日志需要分别记录更新范数与注意力统计，才能判断是哪一层起作用。

## 10. 把公开方法放回四层

前面四个案例说明，“训练稳定方法”并不都作用在同一个位置。下表再加入其他团队的公开方法，标出它们主要处理哪一层：

| 团队              | 代表模型           | 公开方法       | 主要作用层                 |
| ----------------- | ------------------ | -------------- | -------------------------- |
| **DeepSeek**      | R1、V3.2           | GRPO 及改进    | 策略变化                   |
| **阿里 Qwen**     | Qwen3 系列         | GSPO           | 策略变化、MoE 系统         |
| **字节 Seed**     | 豆包 Pro、Seedance | DAPO、VAPO     | 数据与奖励、策略变化       |
| **Moonshot Kimi** | K2、K2.5           | GRPO、MuonClip | 策略变化、数值更新         |
| **智谱 GLM**      | GLM-4.6            | GSPO-style     | 策略变化、MoE 系统         |
| **MiniMax**       | M1、M2             | CISPO          | 策略变化、低精度数值计算   |
| **StepFun**       | Step3              | 多模态训练方法 | 数据与奖励、多模态评测系统 |

这些名称对应的问题并不相同。GRPO、GSPO、DAPO、CISPO 和 VAPO 主要调整策略目标、优势估计或裁剪方式，MuonClip 处理优化器更新。比较方案时要先确认它解决的层级，再判断能否组合使用。

## 11. 模型规模扩大后还要检查什么

### 超大模型与长上下文

- 模型总参数和每次激活参数继续增加，MoE 路由与跨卡通信会成为稳定性指标的一部分。
- 10M+ token 上下文要求训练同时控制显存、注意力数值和长轨迹成本。
- 优化器裁剪只能处理参数更新，仍要配合数据、奖励与系统监控。

### 原生多模态 RL

- 文本、图像和环境动作进入同一条训练轨迹，奖励也要检查跨模态证据。
- Llama 4 的 Early Fusion 展示了从预训练阶段统一模态的一种方案。
- 多模态 RL 需要可重放的图像、视频与交互环境。

### Agentic RL 的工业化

- 训练任务从软件工程扩展到客服、研究和计算机操作。
- Agent 轨迹需要记录工具参数、环境返回和中间状态。
- 长短不一的轨迹增加了环境调度、故障恢复和异步训练成本。

### 训练成本与效率

- 训练成本由预训练、数据生成、Rollout、模型更新和评测共同组成。
- 更高的生成吞吐、更小的激活参数和更准确的数据筛选可以减少无效计算。
- 小团队可以先在可验证的小型任务上复现完整闭环，再决定是否扩大模型和集群规模。

## 12. 四个案例怎样连回排查顺序

四个案例分别落在不同层级：

- **GLM-4.6 与 Llama 4**：MoE、多模态和长上下文改变了训练系统的约束。
- **Seed-Thinking**：数据整理、策略优化、自我验证和课程学习组成推理训练流程。
- **MuonClip 与 QK-clip**：参数更新与注意力计算需要分别控制异常值。
- **不同团队的公开方法**：算法目标、优化器和系统框架需要按作用层级比较。

这些案例分别展示了模型结构、推理训练和数值稳定性怎样影响大规模 RL 训练。

## 13. 本节小结

训练稳定性需要同时观察数据与奖励、策略变化、数值更新和训练系统。排查时也按这个顺序进行：先确认训练目标可信，再看 KL 与熵是否异常，然后检查 loss、梯度和优化器，最后核对生成端与训练端的模型版本和概率。优化器与 clipping 只控制参数更新，不能修复数据、奖励或权重同步问题。

[18.4](./distributed-sync) 将继续展开最后一层问题：当生成、奖励和训练分布在多张 GPU 上时，系统怎样保证数据与模型版本正确流动。
